#### Description

`google/pix2struct-widget-captioning-base` is the Transformers-format release of the Pix2Struct *base* model fine-tuned on Widget Captioning, from "Pix2Struct: Screenshot Parsing as Pretraining for Visual Language Understanding" (Lee et al., arXiv:2210.03347), converted from the T5X checkpoints by the Hugging Face team and pinned here to revision `7e99642f87127dd3aee97ea82616bbfda5e610bb` (the Hub's `main` on 2026-09-14). The snapshot `config.json` declares `Pix2StructForConditionalGeneration`: a 12-layer ViT-style image encoder (hidden size 768, 12 heads, feed-forward width 2048, 16×16 patches with learned row/column position embeddings over a variable-resolution input of up to 4096 patch positions) and a 12-layer T5-style text decoder (hidden size 768, 12 heads of width 64, vocabulary 50,244, `max_length` 20) — 282M parameters in the 1.13 GB float32 `model.safetensors`. The model was pretrained by parsing masked web-page screenshots into simplified HTML and fine-tuned on Widget Captioning (Li et al., 2020: Android screenshots from the Rico corpus with crowd-written descriptions of individual UI elements). The upstream preprocessing indicates the target widget by **drawing its bounds on the screenshot as a blue rectangle with a transparent fill, and renders no header text**; this package reproduces that convention (`annotate_widget`) and disables the header path the snapshot's `preprocessor_config.json` would otherwise switch on (`is_vqa: true`), so no font is fetched and nothing but the box is added to the image. The annotated screenshot is scaled to fill at most 2048 patches while preserving aspect ratio, normalised per image and flattened into patch tokens; the decoder then generates a short caption of the widget's role. Upstream training is not repeated here; what this repository adds is packaging and a bounded adaptation contract: `verify_snapshot` and `stage_missing_files` (manifest digest checking and fresh-clone staging), `Pix2StructWidgetCaptioningPipeline.from_pretrained` (verified local loading with `trust_remote_code=False`), `validate_box` and `annotate_widget`, `caption` (input validation, box rendering, greedy single-beam decoding under a caller-owned `max_new_tokens`, a `truncated` flag), `normalize_caption`, `caption_tokens`, `keyword_hits`, `unigram_f1`, and the `validate_inputs` and `evaluation_report` stage helpers; `predict` / `evaluate` (corpus-level BLEU-4, ROUGE-L, CIDEr-D and unigram F1 against reference captions, from the carried pure-Python `metrics.py`, which also holds the constant-caption and widget-crop colour-neighbour baselines), `adapt` (supervised fine-tuning of the caption decoder's last *k* blocks and final layer norm on validated `{id, image, box, captions}` records, the box drawn exactly as `caption` draws it, every (widget, reference caption) pair a target, validation-CIDEr-D epoch selection, transactional on failure), and `save_artifact` / `load_artifact` / `from_artifact` (a safetensors adapter bound to the pinned base by id, revision and weight digest); and `samples.py`, which downloads one shard of Widget Captioning test widgets (`bevaya/RICO-WidgetCaptioning` @ `6ec57b56…`, CC BY 4.0) whole, refuses it unless its SHA-256 matches the pin recorded by `tools/pin_corpus.py`, and splits a seeded subset of whole apps.

#### Intended Use and Limitations

The uses below are the ones the package was built to support; everything else is either out of scope (§Out-of-scope use cases) or prohibited (§Use cases).

###### Primary Intended Uses

The task is captioning one UI element: input one screenshot (`PIL.Image.Image`, any mode, converted to RGB), one widget box `[x0, y0, x1, y1]` in pixels and a token budget; output one short caption string, the number of tokens generated and whether the budget was exhausted. Envisioned applications are draft accessibility labels (content descriptions) for unlabelled UI elements, to be reviewed by a person before shipping; UI test and automation tooling that wants a human-readable name for an element it already located; and prototyping of screen-reading assistants — with every caption checked against the screen by a person before it is shown to anyone who cannot see it. The pipeline is an inference component and a zero-configuration baseline for widget captioning, not a certified accessibility labeller for any app.

###### Primary Intended Users

Intended users are machine-learning engineers, mobile and web developers, accessibility tooling developers, and researchers integrating widget captioning into research prototypes or in-house tooling. A user is expected to understand that the output is *generated text* — it carries no probability, no correctness signal and no location beyond the box the caller supplied, and the model captions every box, including one on a blank image, with equal fluency — that the box is part of the request (a box around the whole screen still yields a widget-style caption), that captions follow the Widget Captioning style (a few words naming an action or a control: `search bar`, `go to profile`, `select ana`), that the token budget is theirs to set, that the model was fine-tuned on 2017-era Android screenshots at phone resolution so flat mocks, desktop and web UIs, dark themes and non-English interfaces are distribution shifts, that greedy decoding is reproducible on a fixed device but GPU and CPU outputs need not match, and that caption quality can only be measured on reference captions they supply. Users who need widget detection, whole-screen summaries, UI text transcripts or batch throughput are expected to know none of that is provided here.

###### Out-of-scope use cases

1. **Capability boundary:** no widget detection or localisation (the box is an input), no whole-screen description (a separate checkpoint), no confidence, no abstention (the model cannot say "not a widget"), no UI text transcript, no multi-box or multi-screen handling (one box per call; each call is a full encoder pass), no sampling or beam search (greedy, one beam), and no guarantee that the caption names the element's actual function — the smoke run captioned a gear icon `go to next`.
2. **Input boundary:** `caption` rejects non-PIL images (`TypeError`), sides below `MIN_IMAGE_SIDE = 16` px or above `MAX_IMAGE_SIDE = 4096` px, boxes that are not four numbers, lie outside the image or are smaller than `MIN_BOX_SIDE = 4` px on a side, and budgets outside `[1, MAX_NEW_TOKENS = 64]` (`ValueError`/`TypeError`). Every screenshot is scaled to fill at most 2048 patches of 16×16 px, so a `BOX_WIDTH = 3` outline on a very large screenshot may thin to under a pixel after scaling, and small widgets lose detail; the outline width upstream used (Pillow's default on 1440×2560 Rico screens) was not matched exactly.
3. **Input boundary:** the fine-tuning data is Widget Captioning — Android app screenshots from Rico (2017, phone resolution, light themes, English) with captions for elements that have a view hierarchy box. Flat mocks (the tutorial's), desktop and web interfaces, dark themes, games, non-English UIs, screenshots with overlays or notifications, and boxes that do not correspond to a UI element fall outside what the upstream authors evaluated and what this repository measured; results on them are undefined, not merely degraded. A box on an image that is not a screenshot still produces a caption (see §Risks and harms).
4. **Decision boundary:** not for autonomous decisions that act on captions — shipping accessibility labels unreviewed, driving UI automation or agents that click what the caption names, compliance or moderation judgements about an app — without a human comparing the caption with the screen, and a locally measured reference-based score on the deployment's own screens.

#### Factors

###### Groups

This pipeline is not human-centric by design: it describes a UI element on a screenshot and never classifies, identifies or scores people. The fine-tuning data (Rico screenshots captioned by crowd workers) contains no evaluation groups in the demographic sense, and neither the upstream authors nor this repository audited it for anything of the kind. Screenshots can nonetheless contain personal data (names, avatars, messages — the tutorial mock contains fictitious ones), which a caption may repeat (`select ana`). What does vary is the interface population: Rico is 2017 Android, English, mostly light-themed consumer apps, so interfaces in other languages and scripts, desktop and web layouts, dark or high-contrast themes, right-to-left layouts, games and accessibility-mode renderings are the groups whose caption quality is unknown, not known to be equal. Where captions become accessibility labels, the people affected are screen-reader users: a wrong label misleads exactly the user who cannot check it, so the operator who ships labels is responsible for a review process — and for a fairness audit stratified by app type and locale — before any generated label reaches a user.

###### Instrumentation

The upstream pretraining "instrument" is a web renderer (screenshots of pages paired with their HTML) and the fine-tuning instrument is the Rico crawler's screenshots of Android apps at 1440×2560 with widget bounds taken from the view hierarchy and drawn as a blue rectangle. Inference screenshots arrive from whatever produced them — a phone, an emulator, a browser, a design tool, a drawing library — and resolution, scaling, theme, compression and the box's provenance (a view hierarchy, a detector, a human) all change the visual evidence; the 2048-patch budget fixes the encoder's input size regardless of the source, so a small widget on a large screen loses detail while a large blank margin costs patches. This repository draws a 3 px outline at the caller's resolution rather than upstream's default width at Rico resolution, an instrument difference whose effect was measured only on the mock (widths 2 and 5 gave near-identical captions). The pipeline validates type, size and box geometry only; it cannot detect a non-screenshot image, a box that misses its widget, or a theme the model never saw. The synthetic tutorial mock (flat Pillow shapes, Pillow's bundled font, no real app chrome) is itself a rendering instrument unlike any Rico screenshot, which is why its captions are observations, not measurements.

###### Environment

Operating environment: Python 3.12 with `torch==2.14.0`, `torchvision==0.29.0`, `torchaudio==2.11.0`, `transformers==4.57.6`, `safetensors==0.8.0`, `numpy==2.5.3`, `pillow==11.3.0`, float32 on CPU; CUDA is used automatically when visible (float32) but was not exercised for this card. Measured on the reference machine with the GPU hidden (`CUDA_VISIBLE_DEVICES=-1`) and the Hub offline (`HF_HUB_OFFLINE=1`): load 5.36 s (verify of the 8-file, 1.13 GB snapshot included); five widgets on one 540×960 mock at the default budget, 1.96–2.44 s per widget (2–5 tokens); a 4096×4096 blank image 2.66 s — cost is dominated by the 2048-patch encoder pass per widget and only weakly by the caption length. Data environment: the model assumes the image is a phone-app screenshot and the box encloses one UI element; the synthetic tutorial mock violates the first assumption on purpose (flat drawing), which is where the recorded miss comes from. Desktop and web UIs, dark themes, non-English interfaces and boxes that enclose nothing violate it to degrees this repository did not measure, and the pipeline reports no signal when they do.

#### Metrics

###### Performance Measures

The pipeline reports no quality measure. The caption is generated text with no score, probability or correctness signal; `new_tokens` and `truncated` describe the generation, not its quality. Widget-caption quality is conventionally measured with reference-based corpus metrics — CIDEr (the benchmark's primary), BLEU-4, METEOR, ROUGE-L — which need several human-written references per widget and a corpus; the inference stage does not compute them, and the Widget Captioning dataset is not bundled (the tutorial downloads one digest-pinned shard at run time). The repository ships two lighter helpers because they are what a caller can compute on their own labelled sample: `unigram_f1(prediction, references)` — bag-of-words F1 after normalisation (lower-cased, punctuation removed, whitespace collapsed) against the best-matching reference — and `keyword_hits(caption, keywords)`, whole-token presence of caller-chosen keywords. Both are plumbing checks, stated as such. The public `evaluation_report(results, references=None)` stage returns the report in machine-readable form: the mean `unigram_f1` plus one per-widget entry (box, prediction, references, score) with the verdict `sample-sanity` when references are supplied, or the verdict `not-measurable` naming the labelled set that would be required when they are not — which is the tutorial's default path, by design (this profile is report-only). The tutorial notebook uses the package's pure-Python `metrics.py` (corpus BLEU-4, ROUGE-L, CIDEr-D, unigram F1) and measured, on 2026-09-26 in one Kaggle Tesla T4 run, one seeded app-disjoint split of one pinned Widget Captioning test shard (164 test widgets; document frequencies from the references of the evaluated set, so the CIDEr-D values are not comparable to published numbers): CIDEr-D constant caption 0.138 / colour neighbour 0.142 / frozen 1.318 / adapted 1.356; BLEU-4 0.0 / 0.0 / 0.365 / 0.232; ROUGE-L 0.075 / 0.087 / 0.564 / 0.567; unigram F1 0.077 / 0.087 / 0.577 / 0.578; CIDEr-D by category `large-widget` (48) 2.246 → 2.291 and `small-widget` (116) 0.934 → 0.969. These widgets come from the checkpoint's own benchmark test split, so the frozen scores are an in-distribution sanity check, not an independent estimate. The upstream paper's Widget Captioning CIDEr for the base model (upstream-reported; not restated here because the hosted card gives no number) is not reproduced or claimed by this pipeline.

###### Decision thresholds

No score threshold exists in the model: it generates tokens until end-of-sequence or the budget and nothing is filtered or abstained. The decision parameters are the **token budget** `max_new_tokens`, default `DEFAULT_MAX_NEW_TOKENS = 20` (a phrase-sized budget chosen by this repository; the checkpoint's own `text_config.max_length` is 20 and the five smoke captions needed 2–5 tokens including end-of-sequence) with ceiling `MAX_NEW_TOKENS = 64`, and the **box**, which the caller owns entirely: it must enclose the element the caption should describe, and moving or enlarging it changes the caption (a whole-screen box produced `select the message` in the smoke run). A budget that is too small is reported, not hidden: `truncated` is true whenever `new_tokens` reaches it (a budget of 1 yields `go`, truncated), and the caller should raise the budget and rerun. Decoding is greedy (`do_sample=False`, `num_beams=1`) with no temperature, beams or repetition penalty. The box rendering itself is fixed (`BOX_COLOR` (0, 0, 255), `BOX_WIDTH` 3) so that every caller presents widgets the way the model was trained to see them. A deployment owns choosing the budget and producing the boxes, and decides how a caption is verified against the screen before it is used.

###### Approaches to uncertainty and variability

This repository reports no central metric value and therefore no dispersion: the smoke run records timings, token counts and the captions of five widgets on one drawn mock, not quality. Run-to-run variability comes only from floating-point kernel selection across CPU builds and accelerators; there is no sampling and no seed to set, so a fixed input on fixed hardware is repeatable, but because decoding is autoregressive a single differing token changes the rest of the caption, and CPU and CUDA outputs need not match; the mock's bytes depend on the Pillow build's bundled font. On the drawn mock the model captioned the `New message` button `go to new message`, the search field `search bar`, the gear icon `go to next` (the recorded miss), Ana's avatar `select ana` and the Profile tab `profile` — five observations on one flat drawing, four of five expected keywords present, not an estimate; sensitivity probes recorded in the smoke: a red or black outline instead of blue produced `select the picture` for four of the five widgets (the blue convention matters), outline widths 2 and 5 and a 2× upscaled mock produced near-identical captions, an empty rendered header (the snapshot's `is_vqa` path) produced near-identical captions, and a box on a blank white image produced `select the image`, on uniform noise `go to next`, on the whole screen `select the message` — which is what an uncalibrated generator with no abstention looks like. The tutorial's measured scores (see Performance Measures) come from one seed, one split and 164 test widgets, with no dispersion estimate; the adaptation's gain over the frozen model (+0.038 CIDEr-D, with BLEU-4 falling 0.365 → 0.232) is within what a different split could reverse. A caller who needs a quality estimate must supply several reference captions per widget and compute CIDEr/BLEU over a corpus or bootstrap resamples themselves; a caller who needs a confidence per caption has none from this model.

#### Ethical considerations and biases

No external ethics board, red-team, or population-specific clearance reviewed this repository or, to our knowledge, the upstream checkpoint; nothing below should be read as implying one.

###### Data

The upstream paper describes pretraining on 80M masked web-page screenshots paired with simplified HTML (from the C4 corpus's URLs) and fine-tuning on Widget Captioning, whose screenshots come from Rico — 2017 crawls of free Android apps, with whatever user-like content the crawler's interactions produced on screen (account names, messages, contacts, locations) — with crowd-written captions; personal or personal-looking data in the fine-tuning corpus is therefore present by construction, and web screenshots can contain more. Neither was audited here. This repository distributes code, tests, and documentation; it does not distribute the 1,129,177,976-byte `model.safetensors`, which is staged locally under `weights/pix2struct-widget-captioning-base/` and git-ignored, and it ships no real screenshots — the tutorial mock is drawn in code with fictitious names. The operator must audit the screenshots they submit for personal, proprietary, or otherwise restricted content (screens routinely show messages, balances, health data and identities); the pipeline performs no such check and will caption a box around a private message as readily as one around a search bar.

###### Human Life

This pipeline is not intended for decisions in health, safety, criminal justice, employment, credit, or housing, and it has not been validated or certified for any of them by this repository, the upstream authors, or any regulator. Foreseeable but unintended sensitive uses — shipping generated accessibility labels to screen-reader users without review (a wrong label on a `Delete`, `Pay` or `Call 911` control misleads exactly the user who cannot see it), driving UI agents that act on what a caption says a control does, captioning controls in medical, financial, industrial or vehicle interfaces — would be admissible only with human review of every caption against the screen (the model captions any box with equal fluency and gives no signal), a locally measured reference-based score on the deployment's own screens stratified by app type and locale, a documented budget and box policy with `truncated` handling, and whatever regulatory clearance the domain requires.

###### Mitigations

- **Supply-chain integrity:** `MODEL_REVISION` is a 40-hex commit; `stage_missing_files` refuses a manifest whose `modelId`/`revision` differ from the package constants and fetches only manifest-listed files at that revision when `allow_download=True`; `verify_snapshot` then checks all 8 listed files' byte sizes and SHA-256 before any load; `from_pretrained` loads only from the verified directory with `local_files_only=True`, always passes `trust_remote_code=False`, disables the snapshot's header path so **no font is fetched at inference time** (the `ybelkada/fonts/Arial.TTF` download the stock VQA processor performs never happens), and the smoke run loaded and captioned with `HF_HUB_OFFLINE=1`. The upstream `pytorch_model.bin` (pickle) is neither listed nor loaded. A test flips one hex digit of a manifest digest and asserts the loader refuses; another asserts a foreign manifest is refused; the import-boundary tests assert that a missing or tampered snapshot is refused before `torch` or `transformers` is imported; another asserts the blue outline is drawn on a copy and the caller's image is untouched.
- **Input integrity:** the public `validate_inputs(image, boxes, *, max_new_tokens)` stage applies exactly the checks `caption` applies (both route through one shared private checker) and returns an input manifest recording the schema, the ceilings, the observed input, the checked boxes, the budget and the verdict; `validate_image` rejects non-PIL inputs and sides outside 16–4096 px; `validate_box` rejects malformed, out-of-image and too-small boxes and rounds coordinates to integers; out-of-range or boolean budgets are rejected; `caption` raises on a malformed runner result; `evaluation_report` rejects mismatched or empty reference lists; `unigram_f1` rejects an empty reference set.
- **Reproducibility:** exact `==` pins in `pyproject.toml`; greedy single-beam decoding with no sampling; a fixed box colour and width; no header or font on the model path; every result carries `model_id`, `model_revision`, the checked box, the budget, `new_tokens`, `truncated`, the device and the dtype.
- **Refusals:** no batching, no download without the explicit flag, no Hub access at inference time, no sampling, no pickle deserialisation, no attempt to detect widgets or to guess whether a box encloses one, and no filtering of caption content — that policy is the operator's to implement around the pipeline.
- **Adaptation integrity:** `adapt` validates the dataset before any tensor is built, trains only the named tensors with every other parameter's `requires_grad` false, restores the initial tensors and re-freezes the model if anything raises (including the caller's progress callback), and keeps the epoch with the best validation CIDEr-D rather than the last; `save_artifact` records the base id, revision, `model.safetensors` digest, tensor names, file size and SHA-256; `load_artifact` verifies format, version, base, path containment, digest and the exact tensor set (only `decoder.` tensors are accepted) before `safetensors` deserialises anything.
- **Data integrity:** the sample shard is downloaded at an immutable dataset revision and refused unless its size and SHA-256 equal the pins; with no SHA-256 pin recorded the reader refuses to run rather than read an unverified file; the split keeps every app (and so every screen) in one split.
- No statistical mitigation (class balancing, subsampling) applies: the adaptation samples widgets uniformly and the reported metrics are unweighted means; a widget with one reference trains the model on one annotator's phrasing.

###### Risks and harms

- **Invented captions:** the model has no abstention — a box on a blank image yielded `select the image` and on noise `go to next` in the smoke run — so a box that encloses nothing, or an image that is not a screenshot, produces a fluent widget-style caption with no signal; downstream consumers that trust the string (accessibility labels, UI agents, test names) inherit the error silently.
- **Wrong function names:** a caption can name a plausible but wrong action (`go to next` for a settings gear); for controls with consequences (`Delete`, `Pay`, `Send`) a wrong label harms the user who relies on it; only reference-based evaluation on the deployment's screens shows the rate, and the tutorial measures none.
- **Box dependence:** the caption describes whatever the blue outline encloses; a box from a detector or view hierarchy that is off by a few pixels, or a box the caller draws around the wrong element, yields a caption for the wrong thing with no signal — and the outline colour matters (a red or black box degraded four of five captions in the probe).
- **Personal data echo:** captions repeat on-screen names and text (`select ana`); a screenshot with private content produces captions containing it.
- **Automation bias:** a terse, imperative caption reads like a ground-truth label and invites trust that generated text has not earned.
- **Truncation:** a caption longer than the budget is cut (reported via `truncated`); a caller who ignores the flag ships a partial phrase.
- **Bias amplification:** any interface population Rico under-represents (non-English, desktop, dark themes, games, newer design systems) is reproduced as uneven caption quality, undetected because no per-population evaluation exists.
- **Resource use:** a 1.13 GB model and ~2.0–2.4 s per widget on the reference CPU with a 2048-patch encoder pass per widget; a screen with many widgets scales linearly, and the CUDA path was not measured.

###### Use cases

Prohibited even where the model would work: shipping generated captions as accessibility labels, help text or evidence without human review; driving UI agents or automation that act on unreviewed captions in interfaces where actions have real-world consequences (payments, messaging, deletion, device control, medical or industrial controls); captioning screenshots the operator has no right to process, including other people's private screens, messages, financial or health information, or licence-restricted app content; using screenshots or captions to identify, profile or surveil users; and any use that violates the upstream Apache-2.0 licence terms, the terms of the deployment that runs the pipeline, or the consent and data-protection obligations attached to the screens processed. Autonomous high-consequence actions triggered by unreviewed captions are prohibited by the intended-use contract above.

## Input/output contract

- `Pix2StructWidgetCaptioningPipeline.from_pretrained(device=None, weights_dir=None, allow_download=False)` — stages missing manifest files (only with `allow_download=True`), verifies digests, loads; `device` defaults to `cuda:0` when visible, else `cpu`; float32 on both.
- `caption(image, box, *, max_new_tokens=20) -> dict` with keys `caption` (stripped decoded text), `box` (checked, integer `[x0, y0, x1, y1]`), `image_size`, `new_tokens` (end-of-sequence included), `truncated`, `generation` (`max_new_tokens`, `do_sample` false, `decoding` greedy), `device`, `dtype`, `source`, `model_id`, `model_revision`.
- `validate_box(box, image_size) -> list[int]`; `annotate_widget(image, box) -> Image` (RGB copy with the blue outline); `normalize_caption(text) -> str`; `caption_tokens(text) -> list[str]`; `keyword_hits(caption, keywords) -> dict[str, bool]`; `unigram_f1(prediction, references) -> float`.
- Ceilings and constants: `MIN_IMAGE_SIDE = 16`, `MAX_IMAGE_SIDE = 4096`, `MIN_BOX_SIDE = 4`, `BOX_COLOR = (0, 0, 255)`, `BOX_WIDTH = 3`, `MAX_NEW_TOKENS = 64`, `DEFAULT_MAX_NEW_TOKENS = 20`, `DECODING = "greedy"`, `MAX_PATCHES = 2048`, `INPUT_SCHEMA`.
- `validate_inputs(image, boxes, *, max_new_tokens, names) -> dict`; `evaluation_report(results, references=None, *, sample_kind) -> dict` where `references` holds one sequence of reference captions per result; `verify_snapshot(path=None) -> dict`; `stage_missing_files(path=None, *, allow_download=False, downloader=None) -> list[str]`.
- `predict(records, *, max_new_tokens=20) -> list[str]` and `evaluate(records, *, max_new_tokens=20) -> dict` — caption every validated record's widget (at most `MAX_EVAL_RECORDS = 2000`); `evaluate` returns `caption_metrics` plus `verdict` (`measured`, or `measured-small-sample` below `MIN_SCORED_RECORDS = 50`), `adapted`, `seconds`; `adapt(train, val=None, *, epochs=3, lr=1e-5, batch_size=4, trainable_decoder_layers=2, seed=0, progress=None) -> dict` — bounded fine-tuning with validation-CIDEr-D epoch selection, transactional on failure (a batch is `batch_size` widgets with all their references); `save_artifact(output_dir, metadata=None) -> Path`; `load_artifact(artifact_dir) -> dict`; `from_artifact(artifact_dir, *, device=None, weights_dir=None, allow_download=False)` — loads the verified base and then the verified adapter.
- Dataset helpers (`samples.py`): `fetch_corpus`, `read_corpus`, `build_sample_dataset`, `load_byod_dataset`, `validate_dataset`, `split_dataset`, `check_split_disjoint`, `write_dataset_jsonl`, `reference_captions`, `widget_category`, `corpus_pinned`; metrics (`metrics.py`): `bleu4`, `rouge_l`, `cider_d`, `caption_metrics`, `medoid_caption`, `constant_caption_baseline`, `colour_neighbour_baseline`.
